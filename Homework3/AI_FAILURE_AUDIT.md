# AI Failure Audit - Homework 3

Every slice was generated by an AI assistant one prompt at a time,
then reviewed before commit. The defects below were all present in the AI's
first draft and were caught by review. None of them reached a commit.

Verification tools (re-runnable, no dependencies):

```
node tests/countdown.test.js   # fake clock: boundaries, throttled tab, timer count
node tests/form.test.js        # stub DOM: state machine, double submit, XSS
```

---

## Defect 1 - `Intl.DateTimeFormat` option conflict kills the countdown

**Slice:** 1 (countdown) - fixed in commit `787ef83`

### Description
The draft formatted the start time with:

```js
new Intl.DateTimeFormat(undefined, {
  dateStyle: "full", timeStyle: "short", timeZoneName: "short",
})
```

ECMA-402 forbids mixing `dateStyle`/`timeStyle` with individual fields such
as `timeZoneName`, so the constructor throws a `TypeError`. The call ran
before `tick()`, so the countdown stayed at `--` forever and the console
showed an error. The code looked correct and read naturally, which is why it
is easy to accept without running it.

### Diagnostic method
First run of `tests/countdown.test.js` crashed with
`TypeError: Invalid option : option` pointing at the formatter line.
To rule out a harness artifact, it was reproduced outside the sandbox:

```
node -e 'new Intl.DateTimeFormat(undefined,{dateStyle:"full",timeStyle:"short",timeZoneName:"short"})'
-> TypeError
```

### Refactored solution
List the fields explicitly (`weekday`, `day`, `month`, `year`, `hour`,
`minute`, `timeZoneName`), which is a valid combination. A comment in the
code records why `dateStyle` is not used. Each slice also lives in its own
IIFE, so an exception in the countdown can no longer take the form down with it.

## Defect 2 - Off-by-one second at every boundary (`Math.floor`)

**Slice:** 1 (countdown) - fixed in commit `787ef83`

### Description
The draft computed remaining seconds with `Math.floor(ms / 1000)`.
With 2.5 s left it showed `00:00:00:02`, and with 0.5 s left it already
showed `00:00:00:00` while the event had not started. The display was
always one second ahead of reality.

### Diagnostic method
Boundary test in `tests/countdown.test.js` with a fake `Date.now()`:

```
FAIL at 2.5s left: got 00:00:00:02, want 00:00:00:03
```

### Refactored solution
Round **up** to whole seconds before splitting into units
(`Math.ceil(remaining / 1000) * 1000`). The next tick is still scheduled
for `remaining % 1000` ms, exactly when the displayed value changes. A test
with a timer that fires exactly on a boundary (0 ms lateness) confirms the
display never freezes for a second.

## Defect 3 - Stale display after background tab (and the duplicate-timer trap)

**Slice:** 1 (countdown) - fixed in commit `787ef83`

### Description
Recomputing from `Date.now()` avoids accumulated drift, but browsers
throttle timers in hidden tabs (Chrome: about once per minute). After
switching back, the draft could show a value up to 60 s old until the
throttled timer finally fired.

The obvious patch, calling `tick()` again on `visibilitychange`, creates
a **second** `setTimeout` chain next to the first one. Every tab switch
would add another chain: double rendering and a timer leak.

### Diagnostic method
`tests/countdown.test.js` simulates a hidden tab: timers fire 60 s late,
30 s pass, then `visibilitychange` fires.

```
FAIL refresh on visibilitychange: got 00:01:00:00, want 00:00:59:30
```

A second assertion counts pending timers after the event to prove only
one chain exists (`single timer chain after visibilitychange: 1`).

### Refactored solution
- Keep a single `timerId`; `tick()` calls `clearTimeout(timerId)` first,
  so any caller can safely force a refresh.
- `visibilitychange` calls `tick()` when the page becomes visible.
- When the countdown reaches zero, no new timer is scheduled and the
  `visibilitychange` listener is removed, so nothing is left running.

## Other findings (minor)

| Finding | Fix |
|---|---|
| `countdown.nextElementSibling` used to find the note paragraph: breaks silently if markup order changes. | Select `.countdown-note` explicitly. |
| `sanitizeText(value, input.maxLength)`: `maxLength` is `-1` when the attribute is missing, and `slice(0, -1)` drops the last character. | Only cap when `maxLength > 0`. |
| The test's own "no innerHTML" check matched the word in a code comment (false failure). | Match `.innerHTML` property access only. Lesson: verify the verifier too. |

## Takeaway
All three main defects compiled, looked idiomatic, and passed a read-through.
They were only found by **running the code against controlled time**
(fake clock, simulated throttling). Reading AI output is not verification.
